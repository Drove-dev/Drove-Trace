# Errly — Architecture Decision Record

This document explains the structural and technical decisions behind the Errly backend. The goal is not to describe _what_ the code does — the README covers that — but to explain _why_ it was built this way, and what trade-offs were considered.

---

## 1. Overall approach: Modular Monolith

Errly is built as a **modular monolith** rather than microservices.

For a project at this scale and stage, microservices would introduce distributed systems complexity (inter-service communication, independent deployments, network latency) without any meaningful benefit. A modular monolith gives us clear domain boundaries through NestJS modules while keeping the system simple to run, debug, and deploy.

Each domain is fully encapsulated in its own module under `src/modules/`. Modules expose only what other modules need via explicit imports and exports — they do not reach into each other's internals.

If Errly ever needs to scale horizontally, the module boundaries make it straightforward to extract individual domains into separate services without a full rewrite.

---

## 2. Framework: NestJS

NestJS was chosen for three concrete reasons:

**Enforced structure.** NestJS imposes a module/controller/service pattern that keeps large codebases navigable. Every feature follows the same shape — a new developer can open any module and immediately understand where the logic lives.

**Dependency injection out of the box.** DI makes services loosely coupled and easy to test. Mocking a repository in a unit test is a one-line operation because of how NestJS wires its providers.

**Ecosystem fit.** NestJS integrates cleanly with TypeORM, Passport, Swagger, and class-validator — all of which Errly uses. There is no friction between layers.

Express was considered as a lighter alternative, but the lack of built-in structure would have required building conventions manually. At the cost of a slightly heavier framework, NestJS buys consistency and testability.

---

## 3. Layer separation

Every module follows a strict three-layer pattern:

```
Controller  →  Service  →  Repository (TypeORM)
```

**Controllers** handle only HTTP concerns: routing, parsing the request, validating the DTO, and shaping the response. They contain zero business logic.

**Services** contain all business logic: permission checks, grouping logic, orchestration across repositories. They are framework-agnostic — a service does not know it is being called from an HTTP request.

**Repositories** are TypeORM `Repository<Entity>` instances injected via `@InjectRepository`. Raw queries are kept inside services using `createQueryBuilder` when the ORM's default methods are insufficient.

This separation means the business logic is fully testable without spinning up an HTTP server or a real database.

---

## 4. ORM: TypeORM over Prisma

Both TypeORM and Prisma are mature options for NestJS. TypeORM was chosen because:

- It integrates via decorators directly on entity classes, keeping the schema definition co-located with the domain model.
- The `Repository<T>` pattern fits naturally with NestJS's dependency injection.
- `createQueryBuilder` gives full control over complex queries (aggregations, joins, raw counts) without escaping to raw SQL strings.

Prisma generates a separate schema file and a generated client, which adds a build step and separates the schema from the domain model. For Errly's use case, the TypeORM approach is more direct.

## 5. Error grouping: fingerprint strategy

The core analytical feature of Errly is grouping identical errors together rather than storing every occurrence as an isolated record.

When an error event arrives, it carries a `fingerprint` — a hash generated by the client SDK that identifies the error's origin (typically derived from the stack trace, file, and line number). The backend looks up this fingerprint in `ErrorGroup`:

- If it exists → increment `occurrences` and update `lastSeen`
- If it does not exist → create a new `ErrorGroup` with `firstSeen = now`, `occurrences = 1`

This approach keeps the `ErrorGroup` table small and queryable regardless of how many times the same error fires. A loop that triggers the same exception 10,000 times produces one `ErrorGroup` with `occurrences: 10000`, not 10,000 rows that flood the dashboard.

The fingerprint is intentionally generated client-side. This allows SDK authors to customize grouping behavior (for example, grouping by error type only, or including the URL in the fingerprint) without requiring changes to the backend.

## 6. Authentication and authorization

**Authentication** uses JWT via Passport. A global `APP_GUARD` enforces JWT validation on every endpoint by default. Endpoints that need to be public (login, error ingestion) are marked with a `@Public()` decorator that bypasses the guard.

This is the inverse of the common pattern where routes are public by default and protected routes are opted in. The inverted default means a new endpoint is protected unless explicitly marked otherwise — reducing the risk of accidentally exposing a sensitive route.

**Authorization** is role-based via the `TeamMember` pivot entity. A user's role within a team determines what they can access within that team's projects. Admin users bypass team-level filtering and can see all data.

The `UserWithRole` interface — built from the JWT payload and enriched by the JWT strategy — carries the user's team memberships and roles through the request lifecycle without additional database queries per request.

---

## 7. SDK Key design

Each project can have multiple SDK keys. A key identifies the project and environment (dev, staging, production) from which an error originates.

Keys are validated on every ingestion request. The validation is intentionally lightweight — a single `findOne` by key string with a `project` relation. This keeps the ingestion endpoint fast.

Keys are never rotated automatically. Rotation is a manual operation (delete + create) to give teams control over when their SDK configuration changes.

---

## 8. Security decisions

**Password hashing.** bcrypt with a salt factor of 10. This is the industry standard for password storage. The `passwordHash` field is excluded from all query selects by default and never appears in response DTOs.

**Rate limiting.** `@nestjs/throttler` is configured globally. The ingestion endpoint is the most exposed surface of the API — it accepts unauthenticated requests from public-facing apps. Throttling prevents a misconfigured SDK from flooding the database.

**Validation pipeline.** A global `ValidationPipe` with `whitelist: true` and `forbidNonWhitelisted: true` strips any fields not declared in the DTO and rejects requests that include unknown fields. This prevents mass assignment vulnerabilities.

## 9. Infrastructure: Docker Compose

The `docker-compose.yml` defines two services:

```
db       →  PostgreSQL 14.3 on port 5432
backend  →  NestJS app on port 3000
```

The backend depends on `db` and reads configuration from `.env` via `env_file`. The database volume is persisted to `./postgres` so data survives container restarts.

For local development, only the `db` service is typically needed — the backend runs directly with `npm run start:dev` for faster iteration (hot reload, direct access to logs).

For a full containerized environment, `docker-compose up --build` starts both services. The `DB_HOST` environment variable must be set to the service name (`db`) instead of `localhost` when both services run inside Docker — this is the most common configuration mistake and is documented in `.env.template`.

---

## 10. Testing strategy

Unit tests are the primary testing layer. Every service has a corresponding `.spec.ts` file that tests business logic in isolation using Jest mocks for all repositories and external dependencies.

The testing philosophy is: **test behavior, not implementation**. Tests assert what a method returns or throws given a certain input — not which internal methods were called in which order.

End-to-end tests exist in `/test` and cover the application's root module. E2E coverage is intentionally minimal at this stage — the core logic is covered by unit tests, and E2E tests will be expanded as the API stabilizes.

Current status: **104 unit tests passing across 11 suites**.

---

## 11. What was intentionally left out

**Caching.** Redis or in-memory caching was not added. At this scale, PostgreSQL query performance is sufficient. Caching would add infrastructure complexity without a measurable benefit yet.

**Message queues.** Error ingestion is synchronous. For high-volume production use, a queue (Bull, RabbitMQ) between the ingestion endpoint and the processing logic would improve resilience. This is a deliberate omission for the MVP — the architecture does not prevent adding it later.

**Multi-tenancy at the database level.** Data is isolated by team and project relationships, not by separate schemas or databases. This is sufficient for the current use case and keeps the schema simple.
